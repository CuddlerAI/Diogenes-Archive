# 路线模拟器：录 C 之前，先在电脑里把这一遍走一千次

C 里的人是程序操控的（`stage_robot.hpp` 的 `RouteWalker`，按组配置 `takeover.route` 走）。路线一改，
要先回答：两条规则会不会触发、会不会碰到人、第一人称看不看得到人？这个工具把**同一份走路程序**放进一个
按实测校准过的「游戏怎么走路」的模型里，对着 AB 录下的全体人物，用不同的随机种子跑几百上千遍，每一遍按一条
合格的 take 来判。

起因：beach-demo-003 的第一遍 C 只按 W，第一人称（第 8 路）只有 58.7% 的时间看得到人（需求 rev 630 要 ≥ 80%）。
当时的模拟没有这一项，模拟出的约 75% 被放过了。**模拟里有的指标，都要当成必须通过的条件。**

## 用法

```bash
cd engine-data/gta-capture
g++ -std=c++17 -O2 -I native/include tools/route_sim/route_sim.cpp -o /tmp/route_sim

# 1. 做表：AB 的世界遥测（takes/AB/source/master-world-telemetry.jsonl）+ 剧本 → cast.csv、bones.csv
python tools/route_sim/make_tables.py <AB 的 master-world-telemetry.jsonl> <stage-spec.txt> /tmp/tables
#    AB 还没录、或不在采集机上：用剧本自己推演的遥测（位置和 003 的 AB 实录差 0.2 mm 以内，骨骼点差一掌宽；
#    2026-10-13 在 Mac 上用它复现了 003 C 的模拟结果：第一人称平均 87.5%（实录那份表 87.8%），离人最近距离逐项相同）
c++ -std=c++17 -O2 -I native/include native/src/stage_plan_dump.cpp native/src/stage_plan.cpp -o /tmp/plan_dump
/tmp/plan_dump examples/stage-beach-demo.txt examples/stage-calibration.beach-demo.txt > /tmp/plan-world.jsonl
python tools/route_sim/make_tables.py /tmp/plan-world.jsonl examples/stage-beach-demo.txt /tmp/tables

# 2. 跑：路线就是组配置里的 takeover.route
SP=/tmp/tables ROUTE="$(python -c "import json;print(json.load(open('<group.json>'))['takeover']['route'])")" \
  SEEDS=1000 FPMAP=1 /tmp/route_sim
SP=/tmp/tables ROUTE_SIM=/tmp/route_sim python tools/route_sim/stats.py "<路线>" 1000   # 汇总：几成是合格的 take、差在哪
SP=/tmp/tables ROUTE="<路线>" SEEDS=1 VERBOSE=1 /tmp/route_sim                            # 单遍：每次按键和规则触发的时间
```

**转身方式要和组配置的 `turn` 一致**（10-16 起 `TURN="walk 40"`，见下「第一人称转得多快」）；不给就是游戏原速转身（10-09 以前的录法）。
D 的路线（组配置 `seventh.route`，10-16 起）：`KIND=D ROUTE="<路线>"`，不给 `WALKER`（给了就是 10-15 以前的漫步程序，不看路线）。
`C_TOURIST_ONLY=1`：C 只该触发挡游客那条规则（用户 10-15 定），聊天两人的规则触发了算不合格。
`START_MAX=12 TAPS_MAX=0`（10-17 起，配合组配置 `turn` 的 `walk 60 straight`）：起步时身体偏离要走的方向超过 12°、或有一下点按，算不合格——只许在走路中转向。

`route_sim.cpp` 文件头写了全部环境变量。几个常用的：`FPMAP=1` 按每 5 秒打印第一人称看到人的比例（哪一段是空的一眼看出），
`FP_ALL` / `FP_POST` 改第一人称的门限（默认全程 80%、接管后 90%，0 = 不查），`PATHLOG=1` 把逐帧轨迹写到 stderr，
`KIND=D WALKER=1 FP_POST=80` 模拟 D 的漫步程序（D 没有接管，全程都算「接管后」，门限用 D 的 80%）。

一遍算合格：两条规则触发、慢跑者的规则不触发；每个停点都走到、没有因为有人挡路停过；离各人最近不小于
聊天男 0.8 / 聊天女 0.9 / 游客 0.72 / 坐着的人 1.2 / 慢跑者 1.5 m；第一人称达标。另外输出最长站立时间、
追背镜头在身后的比例、最短一次按键（不许碎步，≥ 0.4 秒）。

### 路线选好后、录之前

用出片程序本身算第 1、2 路（第 2 路自由运镜要能生成，第 1 路固定机位要全程拍到玩家）：

```bash
SP=/tmp/tables ROUTE="<路线>" SEEDS=1 SEED0=20260936 PATHLOG=1 /tmp/route_sim 2>/tmp/path.log >/dev/null
PYTHONPATH=. SP=/tmp/tables SPEC=<stage-spec.txt> WORLD=<AB 的 master-world-telemetry.jsonl> SEED=<组配置的 seed> \
  uv run -q --with numpy python tools/route_sim/lanecheck.py /tmp/path.log C
```

### 录完之后

```bash
python tools/route_sim/take_c_check.py <takes/C>          # 离人最近、按键、最长站立、追背、第 1–3 路
python tools/route_sim/first_person_check.py <takes/C>    # 第一人称：有人的时间、空档在哪、每 5 秒的比例（要 ≥ 80%）
python tools/route_sim/presses.py <takes/C>               # 每次按键：按多久、转了多少、挪了多远；点按走成路的次数（单键/双键）
```

这两个要在存着这一遍的机器上跑（要 `source/` 和 `config/camera-tape.json`，先 `stage-take-tape`）。

## 第一人称怎么数（和 `subject_bones.py` 同一个口径）

每个人取 7 个骨骼点（root、spine3、head、左右手、左右脚），投进被控者头部相机的 1920×1080、`FP_MM` 毫米画面
（默认 35 mm，fx ≈ 1867；10-16 以前的组是 18 mm、fx = 960，用 `FP_MM=18` 复现；录完后 `first_person_check.py` 按轨迹里这一路的焦距算）：一个人有 ≥ 4 个点在画面内算「看到人」（更接近需求说的「较多、明显」），≥ 1 个点算「露出一点」；
深度 < 0.3 m 的点不算。视线 = 身体朝向（10-16 起，需方：第一人称跟头、头跟身体、不滞后；`FP_VIEW=camera` 复现 10-07 到 10-15
那版的游戏镜头偏航），俯仰固定 0°、平视（10-18 起，用户定：跟着镜头俯仰时站着也在点头；`FP_VIEW=camera` 时仍按
35°·tanh(镜头俯仰/35)、接管后 20 拍缓入），
眼睛在头骨外 0.20 m、顺着视线（和 `stage_tape.first_person_view`、`_eye` 一致）。接管前（tick < 330）骑在被接管演员头上，
朝他自己的朝向、俯仰 0。接管前的 11 秒改不了（003 里只有约 1.6 秒看得到人），
所以接管后要达到 90% 左右，全程才有 80% 多。

**和出片一致（2026-10-07 起）**：出片和模拟都朝游戏镜头的方向看（需方 10-07：第一人称的转向要跟鼠标）。003 重录的 C
逐帧回放，模拟 84.8%、按交付轨迹数 84.9%。（09-29 到 10-07 出片的视线是在身体朝向 60° 以内规划出来的，模拟用的还是更早的
逐帧公式，对有原地掉头的路线偏乐观 2.5 个点。）录完以 `first_person_check.py` 的结果为准。

**站着转身（2026-10-09 起）**：录制程序站着时让人用游戏的原地转身动作转向（`Input::body_to`），走路程序要等身体对准才按 W；
模拟按 `stage_plan_selftest` 同一个实测转身模型转（多大角度 0.5–1 秒转完）。少了这一步，模拟里的人永远等不到对准、一步不走。

## 第一人称用多大焦距（2026-10-16）

需方嫌 18 mm 的第一人称广角感太强（006 的反馈；10-16 会议给的范围 35–50），需求只许 18 / 24 / 35 / 50 mm 四档。
同一份剧本（推演的表）、`TURN="glide 50 100"`，「半个人以上在画面」的平均（最低）：

| 焦距（水平视角） | C 003 的路线，200 遍 | C 站远些的粗改路线，1000 遍 | D 漫步，1000 遍 |
|---|---|---|---|
| 18 mm（90°） | 85.3%（82.4%） | 87.1%（85.3%） | 88.0%（82.9%） |
| 24 mm（74°） | 76.0% | 84.3%（80.7%） | 86.8%（80.3%） |
| 35 mm（54°） | 48.9% | 78.2%（66.6%） | 85.0%（78.3%，1000 遍 1 遍不合格） |
| 50 mm（40°） | 24.7% | — | 80.7%（73.7%，38% 不合格） |

D 站在舞台前 7–10 米看整群人，焦距影响小；C 停下看人时只隔 1.5–2.5 米，35 mm 下人只剩头和肩。粗改路线 = 前半段不变，
两个停点挪到离人约 3 米（东 (0.7, 1.4) 看聊天女人、西 (-0.6, 0.9) 看坐着的人）、每站 14 秒、少掉一次头。35 mm 的
C 还卡在两段：接管前 11 秒（骑在打电话的人头上，只 ~1.5 秒看得到人）和走到聊天两人 1.2 米内触发规则那段。
**用户 10-16 定 35 mm：C 的新路线 1000 遍到不了 80% 就退 24 mm**（固定机位改 18，每遍又是四档各一次）。
之后用户 10-16 定会上的「35–50」按毫米理解：24 mm 不在需方范围内，**第一人称定 35 mm、不退**（`stage_tape.FP_FOCAL_MM`，
固定机位仍 24）。C 的路线要按 35 mm 设计到 80%：站点离人约 3 米、正对着人，接管前让打电话的人面朝聊天两人（剧本 10-16 已改）。

## 第一人称转得多快（2026-10-13 起）

需方 10-09/10-10：第一人称原地转身超过镜头转速上限（需求 p95 ≤ 90°/s）不能接受，「设计一下路线，不转身，或者降低旋转速度和旋转角度」。
模拟器每遍都报第一人称朝向（游戏镜头的偏航，按出片程序同样平滑）的转速：超过 90°/s、60°/s 的秒数，p95、最大值、角加速度 p95，
以及站着转身的次数和最大角度。站着怎么转由 `TURN` 决定（`stage_robot.hpp` 的 `TurnStyle`，组配置 `turn`）：

| `TURN` | 怎么转 | 模拟里怎么走 |
|---|---|---|
| `game`（默认） | 游戏的原地转身一次转到位，多大角度都 0.5–1 秒 | `body_turn`（10-09 实测模型） |
| `steps` | 游戏的原地转身，每次最多 30°，上一步停稳再转下一步 | 同上，每步 ≤ 30° |
| `glide <°/s> <°/s²>` | 录制程序每帧自己设朝向：最快那么多度每秒，按那个角加速度缓入缓出 | 身体就在程序说的朝向上 |
| `walk [°/s]`（10-16 起） | 程序不替人转身：站着只由路线的 `tap` 点一下键转（≤ 45°，游戏自己转），起步前先转 ≤ 35°；数字是镜头转的最快速度（≤ 60），走路时鼠标按它拐弯 | 点键：0.43 秒、身体挪 0.23–0.33 m、转速 1.4°/s×剩余角度 + 10（45° 时约 70°/s）；起步转身同点键；迈一步 0.58 秒 |

转身超过 100° 时往「看不到人的时间更短」的那一侧转，不一定走近路。站着时镜头跟身体的速度也按转身方式限速
（`Turner::follow_rate`；以前是 300°/s：走完停下时身体落后镜头 15–30°，镜头一下甩过去，D 里有 200–390°/s 的帧）。

003 的剧本（推演的表）上比较，每种 C 200–400 遍、D 50–200 遍：

| | 第一人称有人（平均 / 最低） | 超过 90°/s | 转速 p95 | 角加速度 p95 |
|---|---|---|---|---|
| C 10-09 的路线（每站 8 秒、来回 4 趟），`game` | 87.5% / 83.1% | 7.3–7.7 秒（实录 8.3） | 117°/s | 367°/s² |
| 同路线，`glide 50 100` | 83.2% / 78.9% | 0 | 53 | 116 |
| 同路线，`steps` | 83.7% / 78.5% | 0.2 秒 | 64 | 237 |
| **C 现在的路线（每站 10 秒、来回少一趟），`glide 50 100`** | **85.3% / 81.4%** | **0** | **53** | **112** |
| D 4–6 秒一站，`game` | 83.2% / 79.8% | 8.8–10 秒（实录 11.2） | 116 | 485 |
| 同上，`glide 50 100` | 78.1% / 72.2% | 0 | 60 | 170 |
| **D 9–12 秒一站（`WalkRoom` 现值），`glide 50 100`** | **87.9% / 85.3%** | **0** | **60** | **124** |

`steps` 转速达标，但「转一下、停一下」的角加速度 p95 超过需求的 150°/s²；`glide` 全部达标，代价是脚不迈步（每帧直接设朝向），
**录之前先进游戏看一眼**（RUNBOOK §四）。C 现在的路线 400 遍里 18 遍「接管后」落在 88.4–90.0%（内部余量线 90%），整遍都 ≥ 82.4%；
录完照样以 `first_person_check.py` 为准。

### 选哪种转身（10-13 裁决）

**正方（`glide`）**：转速、角加速度都由程序定，模拟里全部落在需求上限内（C 转速 p95 53°/s、角加速度 p95 112°/s²），
第一人称和脸始终一致；配合路线和停留时间的调整，第一人称看到人的比例 C 最低 81.4%、D 85.3%。

**反方**：每帧直接设朝向，脚不迈步，慢转时近景可能看得出脚底在转（需方 08-07 提过「滑步」）；没进游戏看过；
`SET_PED_DESIRED_HEADING` 是新用到的原生函数，要在采集机编译时确认。`steps` 脚会迈步，但「转一下、停一下」的角加速度 p95 约
237°/s²（需求 150），而且第一人称最低只有 78.5%；只改路线不改转速则做不到（游戏转身多大角度都 0.5–1 秒，掉头必超 90°/s；
2026-10-08 试过的绕圈路线第一人称只有 51–74%）。

**裁决**：003 的组配置用 `glide 50 100`；录之前按 RUNBOOK §四 先录一遍 C 看追背和固定机位里的转身，看得出滑步就换 `steps`，
并在交付说明里写明角加速度。默认（不写 `turn`）仍是游戏原速，旧组不受影响。

## 准不准

拿两条实录的逐帧真值对过（`replay_fp.py` 把实录转成模拟的输入，`truth_fp.py` 按交付轨迹逐帧数）：

| | 实录 | 模拟 | 接管后逐帧判定不同 |
|---|---|---|---|
| 003 第一遍 C（只按 W） | 58.7% | 60.4% | 70 / 3270 帧 |
| 003 重录的 C（斜走） | 86.3% | 86.1% | 9 / 3270 帧 |
| 003 的 D（漫步程序，模拟 100 遍平均） | 91.2% | 91.0% | — |
| 003 重录的 C，10-07 起的视线（朝游戏镜头） | 84.9% | 84.8% | — |
| 003 10-09 重录的 C（只按 W、站着程序转身） | 83.9% | 平均 87.8%、最低 83.9%（200 遍） | — |
| 003 10-09 重录的 D（同上） | 87.3% | 平均 83.2%、最低 80.4%（50 遍） | — |

前三行是 10-07 以前的视线规则（身体朝向 + 60°·tanh），模拟第一遍偏乐观 1.7 个点，重录那遍偏保守 0.2 个点。所以门限留了余量：接管后模拟里要求 ≥ 90%。
差别的来源：骨骼的动作相位（watcher 被打扰后跟 AB 不同步）、玩家头部骨骼的真实位置（模拟用固定高度）。

## 没有覆盖的

- 只模拟走路和规则，没有游戏本身的东西（碰撞、游戏对被挡住的人的反应、地面起伏）；离人距离按身体中心的水平距离算。
- 骨骼来自 AB 实录，被规则打扰的人（看玩家 5 秒再接着演）按他们剧本的那一拍取姿势，实际看玩家时的姿势不同。
- 追背镜头只报「游戏镜头在身体 60° 以内的比例」，不判画面；10-09 起追背由出片程序另算（`stage_tape.chase_lane`），这个比例不代表追背画面。
- 剧本本身（演员两两距离、固定机位拍不拍得全、自由运镜算不算得出）不归这里管，见 `stage-spec-check`
  （`gta_capture/stage_check.py`）；它没查的正是这里查的：玩家的路线、规则触发、离人距离、第一人称。

## 走路中途换键与镜头自己跟随（2026-10-16 win-pc 实测，用户定方案 A）

需方举的大转身是连着换键（W → W+D → S+D → S）。win-pc 上用按键时间表（路线的 `w:2,wd:1,...`，鼠标完全不动）录了一遍 D
（arc-test-1016b，七组）：每换一次键身体 0.5–0.8 秒转到新方向，45° 换键峰值每秒 120–150°、90° 约 200°；按出片程序算第一人称
最快 189°/s、超过 90°/s 共 6.8 秒、角加速度 p95 261、jerk p95 1968，全超需方上限（engine_qc：角速度 p95 90 且瞬时不超 90、角加速度
p95 150、jerk p95 600）。所以**用户定方案 A**：大转身按住一个键、鼠标慢慢拐，走路途中不换键，A/S/D 只用在起步。

模拟器随之改了三处：
- 人走起来时游戏镜头自己往人背后转（`follow_turn`：身体偏 30–60° 时每秒 16°，60–150° 时 22–29°，更大约 14°；站着不转），程序的鼠标顶住它。
- 起步转身按点键的转速转（实测起步 35° 约 60°/s；以前按走路跟随算，起步就有 190°/s，把每次起步都算成超限）。
- 第一人称转动在 1/30 秒的拍上算（跳过的拍插值，和出片一样），按 6 拍平滑（`stage_tape.FP_SMOOTH_TICKS`），报 jerk p95；
  **超过需方转动上限的一遍算不合格**（`TURN_LIMITS=0` 只看不判）。对照（都按 2 拍平滑）：探测那遍模拟 p95 80、角加速度 151、jerk 1192，
  实录 95 / 259 / 1914，模拟偏乐观。

## 35 mm 下的 C、D 路线（2026-10-16 夜）

按方案 A（走路途中不换键、大转身靠鼠标、A/S/D 只用来起步）、35 mm、`TURN="walk 40"`、超转动上限算坏遍，在剧本的新布局上搜
